# Архітектура (стан 0.1)

Відповідає розділу 7 плану v2. Тут — лише те, що вже є в коді, і правила, яких треба дотримуватися далі.

## Шари

```
ConferenceManagerPlugin.php        реєстрація хуків, дій і налаштувань плагіна
classes/
  Core/            адаптер до OJS: ContextGateway, ServiceFactory (єдине місце Repo::, DAORegistry::, Hook::)
  Api/             REST-контролери (PKPBaseController)
  Forms/           форми налаштувань (PKP\form\Form) — лише переносять дані
  Application/     сценарії: InstitutionProfileService, ContextInfo
  Domain/          чистий PHP 8.2: сутності, правила, валідатори, інтерфейси репозиторіїв
  Jurisdiction/    профілі юрисдикції (generic, UA) — теж чистий PHP
  Infrastructure/  БД (query builder Illuminate), журнал аудиту
  Migrations/      ConferenceSchemaMigration + Steps/StepNNNN*.php
templates/         Smarty
locale/{uk,en}/    рядки інтерфейсу
```

Правила перевіряє `ci/check-layers.php`: `Domain` і `Jurisdiction` не імпортують `PKP\`, `APP\` (поза плагіном) та `Illuminate\`; `Repo::`, `DAORegistry::`, `Hook::` — лише в `Core/` і головному класі. Перехід на наступний LTS має зачіпати лише `Core/`, `Api/`, `Forms/` і головний клас.

## Міграції

- Кожна зміна схеми — окремий клас `Steps/StepNNNN<Назва>.php`, що реалізує `SchemaStep` і перевіряє `hasTable` / `hasColumn` перед змінами. OJS повторно запускає міграції плагінів при встановленні будь-якого плагіна й оновленні ядра, тому повторний запуск не повинен нічого змінювати.
- `ConferenceSchemaMigration` знаходить кроки у файловій системі, а не за списком у коді. Причина: під час оновлення пакета запит уже завантажив **стару** версію класу міграції (`Plugin::register()` викликає `getInstallMigration()`), а PHP не перевантажує клас. Файли нових кроків на диску вже нові, і їхні класи ще не завантажені — тому нові кроки виконуються. Це перевіряє `ci/integration/run.sh` (синтетичний реліз з `Step9999UpgradeProbe`).
- Сам `ConferenceSchemaMigration` змінювати обережно: зміна набуває чинності лише з наступного релізу після оновлення.
- `upgrade.xml` обов'язковий у кожному релізі: без нього `PluginHelper::upgradePlugin` міграцій не запускає.
- `down()` навмисно порожній (ADR-5).
- Таблиця `conf_schema_steps` фіксує, які кроки й коли застосовано (діагностика).

## Ізоляція контекстів (модель C)

Кожна таблиця з даними закладу містить `context_id` або успадковує його (`institution_id → conf_institutions.context_id`). Репозиторії завжди фільтрують за контекстом запиту; профіль закладу видаляється каскадно разом із контекстом. Тест `api-smoke.sh` перевіряє, що дані контексту А не видно в контексті Б.

## Профіль закладу й юрисдикції

- `InstitutionProfile` — незмінний об'єкт з локалізованими полями (`LocalizedText`), підписантами й рахунками. Правила валідації — `InstitutionValidator` + `JurisdictionRules` профілю юрисдикції; форма й API використовують однакову перевірку.
- Чернетка профілю для нового контексту береться з назви й контактного email контексту; юрисдикція за замовчуванням — `UA` для основної мови `uk`, інакше `generic`.
- Новий профіль юрисдикції додається хуком `ConferenceManager::jurisdictions` (див. CONTRIBUTING.md) без змін ядра плагіна.

## REST API

Один контролер на шлях `conference` (`/{context}/api/v1/conference/...`). OJS 3.5 дозволяє лише один контролер плагіна на шлях і зіставляє за префіксом (`conference` перехоплює і `conference/editions`), тому нові модулі (видання, рахунки…) додають маршрути до цього ж шляху через окремі класи-реєстратори маршрутів, а не окремими контролерами з тим самим шляхом.
