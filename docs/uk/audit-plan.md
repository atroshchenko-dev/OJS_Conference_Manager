# План аудиту та оновлень плагіна Conference Manager

Версія плану: 1.1 від 17.11.2026. Стан коду: реліз 0.33.0.0, цільова платформа OJS 3.5 LTS (перевірено на 3.5.0-5 і 3.5.0-6, MariaDB і PostgreSQL, PHP 8.2–8.4). Перший аудит за цим планом проведено для 0.33.0.0, його результати — у [звіті](security-audit-0.33.md).

Документ має дві частини:

1. **План аудиту** — що, як і в якому порядку перевіряти. Його може виконати зовнішній аудитор (заклад-партнер) без участі розробників, тому всі об'єкти перевірки названо з шляхами в коді.
2. **План оновлень** — як плагін іде за новими версіями OJS: патчами гілки 3.5, наступною версією 3.6 і далі, а також за PHP, СУБД і сторонніми плагінами.

# Частина 1. План аудиту

## 1.1 Мета й межі

**Мета.** Переконатися перед ширшим впровадженням (пілот → інші заклади → PKP Plugin Gallery), що плагін не відкриває нових вразливостей у OJS закладу, правильно поводиться з грошима й персональними даними і не ламає OJS.

**Межі аудиту:**
- код плагіна в репозиторії на зафіксованому тезі (наприклад, `v0.32.1.1` або перший `v1.0.0.0-rcN`);
- пакет для встановлення `conferenceManager-<версія>.tar.gz`, зібраний `ci/package.sh` (перевірити, що в ньому немає `tools/`, `ci/`, `tests/`, `.github/`);
- поведінка плагіна в чистому OJS 3.5.0-6 на тестовому стенді.

**Поза межами:** сам OJS і PKP-бібліотеки (крім того, як плагін їх використовує), сервер закладу, LiqPay як сервіс, реальні дані закладів.

**Хто проводить.** Внутрішній аудит проводить розробник (перший — у версії 0.33.0.0). Незалежний аудит може провести заклад-партнер: розробник готує пакет для аудитора (п. 1.3), відповідає на питання й виправляє знахідки. Самоперевірку (п. 1.4) роблять до передачі, щоб аудитор не витрачав час на відоме.

## 1.2 Етапи й терміни

Терміни відносні: Т0 — день передачі пакета аудитору.

| Етап | Коли | Хто | Результат |
|---|---|---|---|
| 1. Самоперевірка й закриття відомого | Т0 − 2 тижні | Розробники | Виправлення з п. 1.4, реліз-кандидат |
| 2. Пакет для аудитора | Т0 − 3 дні | Розробники | Тег, стенд, облікові записи, документи (п. 1.3) |
| 3. Вступна зустріч | Т0 | Обидві сторони | Узгоджені межі, канал зв'язку, шкала серйозності |
| 4. Огляд коду й тестування | Т0 … Т0 + 3 тижні | Аудитор | Знахідки в GitHub Security Advisories |
| 5. Виправлення | у міру надходження, строки за п. 1.7 | Розробники | Виправлення в приватній гілці advisory |
| 6. Повторна перевірка | Т0 + 4–5 тижнів | Аудитор | Підтвердження закриття |
| 7. Звіт і публікація | після п. 6 | Обидві сторони | Звіт, опубліковані advisory, реліз із виправленнями |

Обсяг для аудитора: орієнтовно 8–12 робочих днів однієї людини з досвідом PHP/Laravel і вебзастосунків (≈340 класів PHP, 19 скриптів JS, 25 сценаріїв інтеграційних тестів).

## 1.3 Пакет для аудитора

1. **Код.** Тег у репозиторії й пакет `.tar.gz` з контрольною сумою `.md5` з релізу на GitHub.
2. **Стенд.** OJS 3.5.0-6 у Docker, запускається одною командою: `ci/integration/start-ojs.sh mariadb` (або `postgres`), далі `ci/integration/run.sh`. Альтернатива — `ci/demo/start-demo.sh` з демонстраційними даними. Реальних даних закладів на стенді немає.
3. **Облікові записи за ролями** (створюються `ci/integration/lifecycle.php`): адміністратор сайту; менеджер журналу А; менеджер журналу Б (для перевірки ізоляції); менеджер реєстрації; рецензент; автор-доповідач; учасник-слухач; користувач без ролі; неавторизований відвідувач.
4. **LiqPay.** Режим sandbox з тестовими ключами закладу або без ключів (тоді перевіряється лише підпис і логіка за кодом та тестами `OnlinePaymentFlowTest`, `ci/integration/card.sh`).
5. **Документи:** `README.md`, `SECURITY.md`, `docs/architecture.md`, `docs/ojs-3.5-verification.md` (56 перевірених особливостей OJS 3.5), `docs/uk/*.md` за ролями, цей план, `CHANGELOG.md`.
6. **Канал знахідок:** GitHub → Security → «Report a vulnerability» (приватні advisory, як у `SECURITY.md`). Публічні issue для вразливостей не використовуються.
7. **Правила:** не переносити на стенд реальні дампи (зокрема OCS-дамп партнера); не тестувати на продуктивних серверах закладів без окремої згоди; навантажувальні тести — лише на стенді.

## 1.5 Напрями аудиту й контрольні питання

Для кожного напряму: що перевірити, де, як. Позначка **[Т]** — є автоматичний тест, аудитор перевіряє його повноту; **[Р]** — лише ручна перевірка.

### А. Доступ і ролі
- Кожен маршрут API має проміжний шар ролей; дії над конкретним записом перевіряють, що запис належить журналу запиту й, де треба, користувачеві (чужа участь → 403). **[Т]** `api-smoke.sh`, `isolation.sh`.
- IDOR: підставити чужі `id` рахунку, участі, квитанції, сертифіката, сесії в усіх операціях `ConferencePageHandler` (`receipt`, `invoice`, `certificate`, `invitationLetter`, `documents`, `sessionAttendance`, `checkin`, `my`) і в маршрутах `me/...`. **[Р]**
- Ізоляція журналів (модель C): менеджер журналу Б не бачить і не змінює даних журналу А ні через API, ні через сторінки, ні через експорт. **[Т]** + **[Р]** для експорту.
- Сторінка `/index/conferenceSite` і `ConferenceSiteApiController` доступні лише адміністратору сайту. **[Р]**
- Прапорець `canManage` у публічних сторінках не дає менеджеру одного журналу прав в іншому. **[Р]**

### Б. Платежі
- Зворотний виклик LiqPay: підпис перевіряється до будь-якої дії; сума й валюта з повідомлення порівнюються з рахунком; повтор того самого повідомлення не зараховує оплату двічі; повідомлення для рахунку іншого журналу відкидається. **[Т]** `OnlinePaymentFlowTest`, `card.sh`.
- Порівняння підпису стійке до атак за часом (`hash_equals`). **[Р]**
- Стан спроби оплати змінюється атомарно (CAS), ліміт 20 спроб, оновлення при поверненні лише < 1 доби. **[Т]**
- Режим sandbox не можна залишити ввімкненим непомітно для бойових платежів. **[Р]**
- Промокоди: не дають від'ємної суми, не застосовуються двічі, не переносяться між заходами й журналами. **[Т]** `promo.sh`.
- Публікація без оплати заблокована й через інтерфейс, і через `PUT .../publish` API OJS. **[Т]**
- Нумерація рахунків без пропусків і дублів під паралельним навантаженням (MariaDB і PostgreSQL). **[Т]** `load.sh`.
- Перевиставлення рахунку з перенесенням сплаченої суми не дозволяє «зняти» гроші. **[Р]**

### В. Файли
- Квитанції: розмір, тип за вмістом, зберігання поза вебкоренем, ключі за регулярним виразом, доступ лише платника й менеджера реєстрації. **[Т]** частково.
- Логотипи партнерів: лише PNG/JPEG/WebP до 1 МБ; SVG і HTML не проходять навіть з підміненим розширенням; файл не виконується сервером. **[Р]**
- Обхід шляху (`../`) у всіх місцях, де з параметра будується шлях. **[Р]**
- Видалення файлів разом із записом і за строком зберігання (`RetentionTask`). **[Т]**

### Г. Введення й виведення
- XSS: усі поля, які вводить учасник або менеджер (назви, ПІБ, установа, тези, тексти листів, назви партнерів), безпечно виводяться в шаблонах Smarty, компонентах Vue, PDF, ICS, JSON-LD, листах. **[Р]** з переліком полів.
- SQL: усі запити йдуть через query builder з параметрами; немає зібраних рядком `whereRaw`/`DB::raw` з даними користувача. **[Р]** + С4.
- Експорт CSV/XLSX: формули нейтралізовано (є в `CsvTableWriter`; перевірити й `XlsxTableWriter`). **[Р]**
- PDF: mPDF не звертається до мережі й файлової системи за адресами з даних користувача. **[Т]** частково.
- Перевизначення текстів OJS (`wording/`) не вносить HTML без екранування. **[Р]**

### Д. CSRF і сесії
- Усі POST публічних сторінок викликають `checkCSRF()`; усі змінні маршрути API вимагають `X-Csrf-Token`, зокрема для `multipart/form-data`. **[Р]**
- Зворотний виклик оплати — єдиний POST без CSRF; його захищає підпис. **[Р]**
- Автозбереження кроку майстра подання (`js/wizardReview.js`) не дозволяє змінити чужу анкету. **[Р]**

### Е. Персональні дані
- Перелік категорій даних, які збирає плагін, мета й строк зберігання — відповідають текстам повідомлень у профілі юрисдикції UA. **[Р]**
- РНОКПП збирається лише за вмиканням і не потрапляє в публічні сторінки, реєстр свідоцтв, експорт без потреби. **[Р]**
- Згода батьків для неповнолітніх зберігається з версією тексту згоди. **[Т]**
- Вивантаження даних людини (JSON) повне; знеособлення не залишає ПІБ/email у журналі дій, листах, файлах. **[Т]** + **[Р]**
- Злиття користувачів OJS переносить записи плагіна. **[Т]**
- Журнал дій не містить секретів (ключ LiqPay, токени). **[Р]**
- Публічний реєстр свідоцтв показує мінімум даних, номер не вгадується перебором. **[Р]**

### Є. Зловживання й навантаження
- Масова реєстрація ботами, розсилки (`RunCampaignBatch`) лише менеджером і з обмеженням обсягу, QR-квитки й токени check-in не вгадуються. **[Р]**
- Сторінки заходу й програми витримують навантаження конференції (сотні учасників одночасно). **[Т]** `load.sh`.

### Ж. Фонові завдання, міграції, цілісність
- Повторне виконання завдань нічого не дублює (рішення, сертифікати, нагадування). **[Т]**
- Кроки міграції ідемпотентні; встановлення, повторна міграція й оновлення проходять на MariaDB і PostgreSQL. **[Т]** `run.sh`.
- Видалення журналу каскадно видаляє дані плагіна. **[Р]**

### З. Ланцюг постачання й випуск
- Вміст пакета відповідає коду тегу; у пакеті немає службових файлів. **[Р]**

# Частина 2. План оновлень під нові версії OJS

## 2.1 Як випускається OJS і що з цього випливає

- **Патчі гілки 3.5** (`3.5.0-5`, `3.5.0-6`, далі `-7`, `-8`…): виправлення помилок і безпеки, без зміни API за задумом PKP. На практиці навіть патчі міняли поведінку (у 3.5.0-5 зламаний поштовий драйвер `log`, переадресація першого запиту сесії; у 3.5.0-6 OJS сам дає назву завданню планувальника).
- **Наступні версії** (3.6 і далі): змінюють хуки, Vue-інтерфейс, репозиторії, схему БД. PKP чергує LTS і проміжні версії (3.3 LTS → 3.4 → 3.5 LTS). Чи буде 3.6 LTS і коли вона вийде, треба звіряти з офіційними анонсами PKP, коли з'являться бета-версії.
- **PHP і СУБД**: OJS 3.5 вимагає PHP 8.2+. Нові версії PHP заклади ставлять незалежно від нас.
- Заклади оновлюють OJS із затримкою в місяці, тому плагін має **одночасно** підтримувати кілька патчів 3.5, а після виходу 3.6 — дві гілки.

## 2.2 Що в плагіні залежить від OJS

Архітектурне правило (`docs/architecture.md`, перевіряє `ci/check-layers.php`): виклики OJS дозволені лише в `Core/`, `Api/`, `Forms/`, `Pages/` і головному класі; `Domain/` і `Jurisdiction/` — чистий PHP. Тому оновлення OJS зачіпає передусім ці шари.

Перелік точок залежності (тримати актуальним, див. п. 2.6, крок 3):

| Група | Що саме | Ризик змін у новій версії OJS |
|---|---|---|
| Хуки OJS (19) | `LoadHandler`, `APIHandler::endpoints::plugin`, `TemplateManager::display` (4 обробники), `TemplateManager::setupBackendPage`, `Schema::get::publication`, `Submission::validateSubmit`, `Publication::validatePublish`, `Decision::types`, `Workflow::Decisions`, `ReviewAssignment::add`, `Mailer::Mailables`, `UserAction::mergeUsers`, `NavigationMenus::itemTypes`, `NavigationMenus::displaySettings`, `Templates::Index::journal`, `Templates::Article::Details`, `issueform::execute` | Високий: хуки через `Hook::call` позначені в PKP як застарілі й можуть змінити сигнатуру |
| Події Laravel (2) | `SubmissionSubmitted`, `DecisionAdded` | Середній |
| Репозиторії `Repo::` (12) | `submission`, `user`, `issue`, `reviewAssignment`, `decision`, `userGroup`, `submissionFile`, `publication`, `emailTemplate`, `eventLog`, `section`, `emailLogEntry` | Середній: PKP поступово переводить сутності на Eloquent (як `UserGroup` у 3.5) |
| DAO (4) | `NavigationMenuDAO`, `NavigationMenuItemDAO`, `NavigationMenuItemAssignmentDAO`, `ReviewFilesDAO` | Високий: DAO — кандидати на заміну |
| Інтерфейс Vue | 27 компонентів через `pkp.registry.registerComponent`, `storeExtendFn('workflow', 'getActionItems' / 'getSecondaryItems')`, стан `steps` майстра подання, `reviewSteps` | Найвищий: бекенд OJS активно переписується |
| Шаблони й тексти | Власні шаблони `templates/`, перевизначення текстів OJS `wording/{uk,en}/frontend.po` (24 рядки) через `Locale::registerPath` | Середній: ключі текстів OJS можуть зникнути або змінитися |
| Інфраструктура | `PKPScheduler`/`registerSchedules`, черга `BaseJob`, `RateLimiter`, mPDF 8.2.5 з DejaVu у складі OJS, `UploadedFile`, маршрутизація API Laravel | Середній |
| Обхідні рішення під конкретні патчі | назва завдання планувальника (3.5.0-5), переадресація першого запиту й поштовий драйвер `log` у тестах (3.5.0-5), `#step` у майстрі подання (0.32.0.1), `Locale::registerLoader` не працює в 3.5.0 | Кожне треба переглянути, коли змінюється мінімальна версія |
| Сторонні плагіни | TIB Conference (`stable-3_5_0` @ 88eb249), Google Scholar (заміна заголовків), теми Default, Manuscript, Health Sciences, Crossref | Середній |
| Інструменти OCS | `pkp/ocs` b24cc4c, `pkp-lib` a1fb264, `jonasraoni/ocs-to-ojs` 94b421e, образ OJS 3.4.0-9 → 3.5.0-6 | Низький: потрібні лише для одноразового перенесення |

## 2.4 Процедура: новий патч OJS 3.5 (`3.5.0-N`)

Ціль — заявити сумісність не пізніше ніж через 2 тижні після виходу патча.

1. **День 0–2.** Додати тег у матрицю CI (`.github/workflows/ci.yml`, job `upgrade`, і `stan-ojs`) і в `ci/integration/start-ojs.sh` як значення за замовчуванням. Запустити повний ланцюг на MariaDB і PostgreSQL.
2. Переглянути примітки до випуску й diff `pkp-lib` між патчами за файлами, де визначені хуки й класи з п. 2.2.
3. Якщо все зелене — пройти посібник `docs/uk/walkthrough.md` скриптом `ci/docs/walkthrough.sh` (знімки екрана показують зміни інтерфейсу OJS) і 25 сценаріїв пілота вибірково.
4. Якщо патч виправив помилку, яку плагін обходить, — залишити обхід, доки підтримується старіший патч, і позначити його до видалення (п. 2.6, крок 4).
5. Реліз плагіна з рядком у `CHANGELOG.md` «Перевірено з OJS 3.5.0-N» і оновленими вимогами в `README.md`.
6. Якщо патч — безпековий: перевірити, чи не змінює він поведінку, на яку спирається плагін (CSRF, сесії, ролі API), і за потреби випустити плагін позачергово.

## 2.5 Процедура: нова версія OJS (3.6 і далі)

Ціль — випустити сумісну версію плагіна не пізніше ніж через 1–2 місяці після стабільного релізу OJS, щоб заклади не чекали на плагін.

| Крок | Коли | Що |
|---|---|---|
| 1. Розвідка | Вихід першої бети OJS | Окрема гілка `ojs-3.6`; CI проти бета-образу; перелік того, що зламалося. Звірити кожен пункт п. 2.2 з новим кодом, як це зроблено в `docs/ojs-3.5-verification.md`, і завести новий документ `docs/ojs-3.6-verification.md` |
| 2. Адаптація | Бета → RC | Зміни лише в `Core/`, `Api/`, `Forms/`, `Pages/`, головному класі, JS і шаблонах. `Domain/` не міняти. Нові обхідні рішення — з позначкою (п. 2.6, крок 4) |
| 3. Міграції | Разом з адаптацією | Перевірити, що кроки `StepNNNN` відпрацьовують і на чистій 3.6, і при оновленні OJS 3.5 → 3.6 з наявними даними плагіна (новий сценарій у `run.sh`) |
| 4. Повний цикл | RC OJS | Увесь ланцюг інтеграційних тестів, посібник зі знімками, a11y, сумісність тем і TIB Conference |
| 5. Випуск | Стабільний OJS | Нова лінія версій плагіна (п. 2.7), оновлений запис у PKP Plugin Gallery, інструкція для закладів (п. 2.8) |

## 2.6 Що варто додати в репозиторій, щоб план працював

1. **Таблиця сумісності** в `README.md`: версія плагіна → версії OJS, PHP, СУБД, перевірені в CI. Зроблено в 0.33.0.0.
2. **Нічна збірка проти найновішого патча.** Зараз нічний запуск (`schedule` у `ci.yml`) іде на закріплених `3_5_0-6` і `3_5_0-5`. Додати рядок матриці, який сам визначає найновіший тег `3_5_0-*` і не блокує релізи, але сповіщає про падіння.
3. **Скрипт перевірки API OJS** `ci/check-ojs-api.php`: збирає з коду плагіна всі хуки, `Repo::`, DAO, класи `PKP\`/`APP\` і перевіряє, що вони існують у вихідному коді заданої версії OJS. Дає перелік ризиків для нової версії за хвилину, а не за день ручного пошуку.
4. **Позначки обхідних рішень** у коді: коментар `OJS-WORKAROUND(3.5.0-5): опис` біля кожного обходу. Перед підняттям мінімальної версії OJS — `grep OJS-WORKAROUND` і видалити непотрібні.
5. **Dependabot** для дій GitHub (див. С2) і для `composer.json` (dev-залежності). Зроблено в 0.33.0.0.
6. **PHP 8.5** у матрицю `unit`, щойно OJS 3.5 офіційно його підтримає.

## 2.7 Гілки й нумерація версій

- Зараз: `develop` → `main`, одна лінія під OJS 3.5.
- Після виходу 3.6: гілка `stable-3_5` для виправлень під OJS 3.5 (лише безпека й критичні помилки), `develop`/`main` переходять на 3.6.
- Нумерація: OJS вимагає чотири числа й монотонне зростання для одного плагіна. Пропозиція: `1.x.y.z` — OJS 3.5, `2.x.y.z` — OJS 3.6. Тоді з номера видно, під яку версію OJS пакет.
- Термін підтримки старої лінії: виправлення безпеки щонайменше 12 місяців після виходу лінії під нову версію OJS або доки PKP підтримує відповідну версію OJS — що настане раніше. Супроводжує одна людина (розробник), тому одночасно підтримуються не більше двох ліній: поточна й попередня.
- `upgrade.xml` і новий номер у `version.xml` — у кожному релізі (без цього OJS не запускає міграції).

## 2.8 Інструкція для закладів: як оновлюватися

Розділ «Як оновлювати плагін разом з OJS» є в [посібнику адміністратора сайту](site-admin.md). Коротко:

1. Резервна копія БД і каталогу `files_dir` (зворотних міграцій немає, `down()` навмисно порожній, тож відкат — лише з копії).
2. Перевірити таблицю сумісності: чи є версія плагіна під нову версію OJS.
3. Порядок: спершу оновити плагін до останньої версії під поточний OJS, потім оновити OJS, потім встановити версію плагіна під новий OJS.
4. Після оновлення: «Адміністрування → Очистити кеш шаблонів і даних», перевірити `scheduler.php list` (завдання плагіна на місці), відкрити сторінку заходу й кабінет учасника.
5. Куди повідомляти про проблеми: GitHub Issues, про вразливості — приватно (`SECURITY.md`).
